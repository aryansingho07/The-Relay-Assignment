THE RELAY / Python implementation

Benchmark scope: local stand-in. Hosted Groq measurements and provider calibration are pending.

1. What I built and why

Model planning, BM25 retrieval tool, model extractive drafting, local quotation/citation verification, then model relevance checking and output. The decisive choice: buffer until verification. Admission bounds concurrency and queue depth; a deadline includes waiting and retries. Citations retain PDF page and arXiv version. The semantic checker remains fallible.

2. The real service and my stand-in

Real account limits, latency and recovery were not measured. Groq documents organization-wide quotas and HTTP 429 with Retry-After. Its requests header means daily requests; its tokens header means minute tokens. The HTTP/SSE stand-in has lognormal prefill, token pacing, injected errors/tails, load-sensitive delays and rolling quotas. Defaults are assumptions. The real command fits prefill median/log dispersion only; provider queues and correlated failures remain unknown.

3. Results

The stand-in burst completed 5 of 60 requests. Total-time percentiles include immediate rejections, which can drive the median down as completion falls. First-token percentiles count requests that emitted verified output. The tables use wall-clock measurements from results.csv.

4. Where the time goes

<b>steady-balanced-0008</b> took 2,070.9 ms: 0.0 ms waiting, 1,656.9 ms working and 414.0 ms in retry waits. The first verified token appeared at 1,248.0 ms, leaving 822.9 ms after it. The trace timestamps the retry waits before output. Working includes the model, network, retrieval and output pacing.

5. When a limit is hit

An admitted request can wait for one retry per stage after a minute-limit 429. The original deadline still applies. A full queue rejects new arrivals. Low token headroom reduces passage count, which can weaken evidence coverage. Daily exhaustion opens a circuit breaker and returns the budget message to queued and new requests.

Retrieval: quality versus cost

Table 3 compares page-local pieces and lexical phrase re-ranking. <b>small</b> had the highest combined score for correct answers and correct refusals, and used the fewest tokens. Load runs used balanced. Under token pressure the pipeline fetches two passages. The 18-question development set guided retrieval changes. The stand-in checks quotation structure and the grading rubric uses keywords and citation pages.

How this library will mislead a naive retriever

Repeated titles: "Which optimizer trains the Transformer?" can retrieve the author block. Adjacent translation results: "What English-to-German BLEU?" can return English-to-French BLEU. Different latency definitions: "Moshi theoretical and practical latency?" can retrieve an ablation's theoretical delay while omitting the practical figure. Title stripping helps; neither citation syntax nor lexical overlap proves relevance.

6. Retries

Each stage can retry a transport error, malformed JSON or transient HTTP response once. Authentication and daily limits fail immediately. In the paired stress test, request 0001 hit a repeatable planning fault. Table 2c shows the added wait and the same terminal error. Retries also raised the scenario timeout rate in Table 2b.

7. What the person sees

At 3pm: "The model budget for today is exhausted. I cannot safely finish your answer now. Please try after the provider quota resets; your request has not been left waiting." The stand-in assumes a UTC-midnight daily reset; Groq reset timing was not measured.

8. What I'm unsure about, what I left out, what I learned

Independent lognormal latency is least certain; correlated congestion would make tails optimistic. Deliberately omitted: distributed scheduling and a neural reranker. Lesson: a citation proves where words occur, not that they answer the question. The keyword/page rubric can overcount correctness or miss valid wording; stored answers need manual review.
